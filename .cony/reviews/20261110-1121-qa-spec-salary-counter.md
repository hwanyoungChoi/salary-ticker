# salary-counter 스펙 — qa 검토
날짜: 2026-11-10

## 판정: 조건부 찬성
D1 A 찬성 · D2 A 조건부 찬성 · D3 B 조건부 찬성. 조건은 아래 "조건" 참고.

## 예시 값 계산 (AC-2, AC-3)
- 일급 52,000,000 / 260 = 200,000 (정확). 초당 52,000,000 / (260 x 32,400) = 6.1728 -> "6.2" (P10 표기 맞음).
- 13:30:00 = 16,200초. 16,200 x 52,000,000 / 8,424,000,000... 정수로 8.424e11 / 8.424e6 = 정확히 100,000. 맞다.
- 문제: AC-2 예시가 전부 딱 떨어지는 값(0, 100,000, 200,000)이라 **버림과 반올림을 구분하지 못한다.** 반올림 구현도 통과한다. 딱 떨어지는 경계에서 Double이 99,999.99...로 나오는지는 잡지만, 반대 방향(올림/반올림)은 못 잡는다.
- 추가할 예시(월요일, 연봉 52,000,000):
  - 09:00:01 -> 6 (6.17, 반올림이어도 6)
  - 09:00:03 -> 18 (18.52, 반올림이면 19이므로 구분됨)
  - 09:00:04 -> 24 (24.69, 반올림이면 25)
  - 17:59:59 -> 199,993 (199,993.8, 반올림이면 199,994) 퇴근 직전 경계
  - 12:00:00 -> 86,400... 정확히 3시간 = 10,800초 -> 66,666.67이라 66,666 (3시간 지점, 버림 구분)
- 월요일 날짜는 달력으로 못 박을 것: 2026-11-09(월), 2026-11-14(토). "월요일"이라고만 쓰면 테스트가 날짜 계산을 틀릴 수 있다.

## 근거
1. AC-2/3은 순수 함수(연봉 + 시간표 + Date + Calendar)로 판정 가능하고, 구조 요구가 Calendar·시각 주입을 명시해 충분히 테스트 가능하다. [위험] 표시도 적절(돈 계산).
2. AC-4 [위험]은 "저장된 값이 재시작 후 살아 있다"인데, 자동 테스트는 UserDefaults(suiteName:)를 주입해 저장/읽기까지만 가능하고 `swift run` 재실행은 수동이다. 저장 키·파싱을 UI 밖에 두면 가볍게 검증된다.
3. AC-1, 6, 화면 문구는 메뉴바 앱이라 자동 UI 테스트가 사실상 불가능해 화면 확인으로 간다. 테스트를 늘릴 곳이 아니다.

## 스펙에서 빠졌거나 모호한 것 (테스트 판정에 영향)
- **0 나누기**: P3 초당 = 연봉 / (52 x 주 근무일수 x 하루 근무초). 근무 요일을 모두 끄면(AC-8) 분모가 0이다. 초당 금액 표시와 일급 계산이 크래시하거나 inf/NaN이 된다. 요일 없음일 때 초당 금액 표시값(0? 안내 문구?)을 스펙에 정해야 한다. AC-8은 "매일 0"만 말하고 패널의 초당 금액을 말하지 않는다.
- **Int 오버플로(D3 B)**: A5가 "상한 없음, Int 범위면 받음"인데, 경과초 x 연봉은 연봉이 약 2.8e14(Int.max / 32,400)를 넘으면 오버플로로 **크래시**한다. AC-5는 "앱이 죽지 않는다"를 요구하므로 충돌한다. 연봉 상한을 두거나(예: 1e12) 오버플로 시 처리 방식을 스펙에 적어야 한다. 입력 "9223372036854775807"이 경계값 테스트가 된다.
- **초 미만 시각**: Date는 소수 초를 가진다. 09:00:00.9를 0초로 보는지(버림) 명시가 없다. 경과초는 정수 초로 내림한다고 못 박아야 1초 틱이 흔들려도 단조 증가가 보장된다.
- **시간대**: 테스트는 `Calendar`에 고정 TimeZone(Asia/Seoul)을 넣어야 CI·다른 지역 맥에서 안 깨진다. 구조 요구에 "TimeZone 포함 Calendar 주입"이라 한 줄 적으면 충분.
- **입력 파싱 규칙**(AC-5): 허용 형식이 "쉼표 허용"뿐이다. 경계: 빈 문자열, 공백만, "52,000,000", " 52000000 ", "52000000.5", "1e7", 전각 숫자, 앞자리 0 ("0052"), "-1", "0", Int 범위 초과 문자열. 판정 함수를 `parse(String) -> Int?` 순수 함수로 두면 한 표로 끝난다. 어느 것이 유효한지 기대값을 스펙이 정해 주길 권한다(소수·공백 허용 여부).
- **AC-8 순서 문제**: 시작을 19:00으로 올리면 저장된 종료 18:00과 충돌해 거부되는데, 사용자는 종료를 먼저 늦춰야 한다. 의도된 동작인지 확인 필요(테스트는 "같거나 이르면 거부, 1분 차이는 허용"으로 판정). 분 범위(0...1439), 종료 1440 허용 여부도 모호.
- **시나리오 4 문구**: "다음 근무일 출근 시각 전까지(자정에) 0으로"는 P5(자정)와 표현이 섞여 있다. P5 기준(자정)으로 통일하면 AC-2의 "18:00 이후~23:59:59 -> 200,000"과 일치.
- 저장된 `workWeekdays`에 범위 밖 값/중복이 들어 있어도 크래시하지 않는지는 낮은 우선순위(기기 내부 값이라 사용자가 못 넣음). 무시해도 된다.

## 구조 요구 충분성
충분. 보완 두 가지만:
- 계산 함수가 `Date`, `Calendar`(TimeZone 포함)를 인자로 받는다고 명시.
- 저장소는 `UserDefaults` 인스턴스를 주입받는 얇은 래퍼 또는 키 상수 + 순수 파싱으로 두어, 테스트가 사용자 실제 저장값을 건드리지 않게 한다.

## 테스트 계획(가볍게)
- 자동(핵심): AC-2 표 + 위 추가 예시, AC-3 단조성(하루 32,400초를 전부 돌려 직전 값 이상인지, 반복 연산이 싸다), 연봉 파싱 표, AC-8 검증 함수 경계(같음/1분 차이/역전), 0나누기·큰 연봉 크래시 없음. [위험] 항목(계산, 저장 키)만 버그 되살리기: 버림을 반올림으로, 곱셈/나눗셈 순서를 바꿔 실제 실패하는지 1~2개 확인.
- 수동(`swift run`): AC-1, 4, 6. 아래 "화면 확인" 참고.
- 포맷터: 0, 999, 1,000, 200,000, 1,234,567의 쉼표 한 표.

## 화면 확인: qa가 할 수 있는 것과 없는 것
- Playwright는 네이티브 메뉴바 앱에 쓸 수 없다. 대안은 `swift run`으로 띄운 뒤 `screencapture -R <메뉴바 영역>`으로 메뉴바 일부를 찍는 것인데, 화면 기록 권한이 필요하고 샌드박스에서 막힐 수 있다.
- 할 수 있음(조건부): 메뉴바 숫자 모양(쉼표, 단위 없음)을 캡처로 확인, 1~2초 간격 두 장으로 숫자 증가 확인. 이는 권한이 허용될 때만이고, 안 되면 "화면 확인 못 함".
- 할 수 없음: 메뉴바 항목 클릭으로 패널 열기(접근성 권한 필요), 입력칸 타이핑, 고정폭 숫자로 다른 아이콘이 안 흔들리는지(눈으로 본 연속 프레임 필요), ⌘Q 동작.
- 사람 확인 필요: 패널 열림/입력/종료 흐름(AC-6), 메뉴바 폭 흔들림, 라이트/다크 메뉴바 가독성, 잠자기 후 깨어남(AC 시나리오 5).
- 네트워크 없음(AC-4): 자동 확인은 소스에서 `URLSession`·`URL(` 사용 grep, 실행 중 `lsof -i -a -p <pid>`로 소켓 확인 정도. 완전 증명은 아님.
- 타이머 1초 갱신 자체는 테스트하지 않는다(A3: 표시는 매번 재계산이라 계산 함수 테스트로 충분).

## 결정 필요 항목
- **D1 A: 찬성.** 근거: 기존 테스트가 `@testable import SalaryTicker` 방식이라 이미 동작하고, 계산을 순수 함수로 두면 target 분리 없이 테스트된다. 조건: 계산·포맷·파싱·검증은 `@main`/View 파일과 다른 파일에 두어 View 의존이 없게 한다. 리스크: executable target을 testable import하면 빌드가 느려질 수 있으나 가볍다.
- **D2 A: 조건부 찬성.** 조건: `@AppStorage` 직접 사용 시 테스트가 실제 저장소에 닿으므로, 키 상수와 읽기/쓰기·검증을 UserDefaults 주입 가능한 곳에 둔다(`UserDefaults(suiteName:)`로 테스트 후 삭제). 키 이름·타입을 데이터 모델로 고정한다는 점은 테스트에 유리. 잘못된 입력 시 이전 값 유지(AC-5)는 `@AppStorage` 바인딩에 TextField를 바로 묶으면 지켜지지 않으므로 검증을 거쳐서만 쓰도록 요구.
- **D3 B: 조건부 찬성.** 근거: 정수 연산이 부동소수 오차를 구조적으로 없앤다. 조건: (1) 오버플로 방어(연봉 상한 또는 `multipliedReportingOverflow`) 필수 — 현재 A5와 충돌, (2) 곱셈 먼저/나눗셈 나중 순서를 테스트로 고정(추가 예시 09:00:03 -> 18, 17:59:59 -> 199,993), (3) 나눗셈 분모 0 방어.

## 리스크
- 높음: 큰 연봉 오버플로 크래시(AC-5 위반 가능), 근무 요일 0개일 때 0 나누기(AC-8).
- 중간: AC-2 예시가 버림/반올림 비구분. 시각 고정 테스트가 시간대에 의존.
- 낮음: 메뉴바 시각 확인은 대부분 사람이 해야 함. 이는 수용하되 "사람 확인 필요"로 기록.

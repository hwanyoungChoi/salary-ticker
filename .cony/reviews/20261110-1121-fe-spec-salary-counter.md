# salary-counter 스펙 — fe 검토
2026-11-10

## 판정: 조건부 찬성

## 근거
1. 실현 가능하다. macOS 14 MenuBarExtra(.window) + 상태 변경으로 라벨 1초 갱신, 패널 TextField 모두 가능. 계산을 "현재 시각으로 매번 재계산"(A3)하는 설계는 타이머 지연·잠자기에 안전하다. (확인한 사실: Package.swift는 executableTarget + testTarget(dependencies: SalaryTicker) 구조, 테스트 파일은 이미 @testable import 방식)
2. 산식 검증: 52,000,000 / (52*5*32,400초=8,424,000) = 6.1728/초. 13:30은 16,200초 경과 → 52,000,000*16,200/8,424,000 = 100,000 정확히 나눠떨어짐. 퇴근 시 200,000. AC-2 기대값과 일치한다(추론: 손계산).
3. AC가 시각 고정 단위 테스트로 닫히고 `[위험]` 표시가 적절하다. 태스크 1이 단독으로 엔드투엔드 동작한다.

## 결정 필요 항목
- D1 찬성(A). 실행 파일 target + @testable import는 SwiftPM이 지원하고 현재 테스트가 이미 그렇다. 단 @main App이 있는 target을 import할 때 빌드 경고/링크 이슈가 나면 그때 보고한다. 순수 타입은 App 파일과 분리해 두면 B로 옮기기도 쉽다.
- D2 조건부 찬성(A). 조건: `@AppStorage`는 [Int]를 지원하지 않는다(Int/String/Bool/Double/Data/URL/RawRepresentable만). `workWeekdays`를 "타입 그대로" 고정하면 구현 불가이므로 "UserDefaults 저장, 키 이름 고정, 배열은 UserDefaults.array 직접 접근 또는 RawRepresentable(콤마 문자열) 래퍼는 fe 재량"으로 문구를 바꿔 달라. 연봉 입력은 TextField 로컬 문자열 상태에 두고 유효할 때만 저장하므로 @AppStorage를 TextField에 직접 바인딩하지 않는다.
- D3 조건부 찬성(B 정수). 조건: A5 "Int 범위면 받는다"와 충돌한다. 연봉*경과초가 Int64를 넘으면 trap으로 앱이 죽는다(예: 입력 9e18). AC-5 "앱이 죽지 않는다" 위반. 해법 중 택일 요청: (a) 입력 상한을 둔다(예: 1e12 미만이면 1e12*32,400=3.2e16으로 안전), (b) multipliedReportingOverflow/Double 폴백. (a)가 단순해 추천 — A5 수정 필요. 또한 근무 초를 기준으로 정수 나눗셈(버림)하므로 AC-3 단조성은 자연히 만족한다.

## 리스크 / 확인 요청
- R1 (높음) `swift run` 번들 없는 실행에서 패널 TextField가 키보드 포커스를 못 받을 수 있다. 앱이 activation policy를 갖지 않아 윈도우가 key가 안 되는 흔한 문제. `NSApplication.shared.setActivationPolicy(.accessory)` + `NSApp.activate`가 필요할 수 있고, 이는 Dock 아이콘 숨김을 겸한다. "Dock 숨김은 .app 패키징 이후"(다음 단계 후보)와 겹치므로, 태스크 1에서 필요하면 넣어도 되는지 허용 문구가 필요하다. 구현 전 최소 스파이크로 확인한다.
- R2 (중) 메뉴바 라벨에서 TimelineView는 갱신이 불안정하다고 알려져 있다. @Observable 모델 + Timer(.common 모드)로 Text 라벨을 갱신하는 쪽으로 간다. 화면 확인은 qa가 `swift run`으로 해야 한다.
- R3 (중) 고정폭 숫자: 메뉴바 라벨의 Text는 .monospacedDigit() 등 폰트 수정자가 무시될 수 있다. 스펙이 "안 되면 보고"로 열어 두었으므로 충분하다. 실패 시 폭 흔들림 허용으로 합의 요청.
- R4 (낮음) 정각 경계: 18:00:00은 200,000, 09:00:00은 0으로 경계를 포함/미포함 구분 없이 클램프(0...근무초)하면 일관. 자정 리셋은 Calendar.startOfDay 기준, "오늘이 근무 요일인가"는 Calendar.component(.weekday)로 판단. 테스트는 Calendar에 고정 TimeZone을 넘겨 기기 설정과 무관하게 한다.
- R5 (낮음) 태스크 2의 근무 요일 수가 바뀌면 연간 근무초 = 52*요일수*하루초. 요일 0개면 0 나눗셈이므로 0 반환 처리 필요(AC-8 "매일 0"과 일치).
- R6 (낮음) A4: 번들 없는 실행의 UserDefaults 도메인은 실행 파일 이름 기준이므로 `swift run`끼리는 유지된다. 단 qa가 값을 초기화하려면 `defaults delete SalaryTicker` 방법을 알아야 한다. 구현 기록에 남기겠다.

## 태스크 분해 / AC 의견
- 1-3 테스트를 1-1과 같이 가는 것이 자연스럽다(계산 함수와 테스트 동시 작성). 순서만 조정이고 분해는 적절하다.
- AC-1 "1초마다 올라간다"는 시각 확인 항목이다. 근무시간 밖에는 검증이 어렵다. qa가 시스템 시각을 바꿀 수 없으므로, 계산 함수의 현재 시각 주입과 별개로 앱에서 확인하는 방법이 필요하다. 근무시간 밖이면 AC-1은 기본 시간표에 의존하므로 qa가 근무시간 중에 실행하거나, 태스크 2 이후에 시간표를 지금 시각 포함으로 바꿔 확인한다고 AC에 한 줄 적기를 권한다.
- AC-4의 "네트워크 요청 없음"은 코드에 URLSession 등이 없음을 확인하는 것으로 충분하다고 명시하면 좋다.
- AC-8 "이유 표시"의 문구 지정이 없어 qa 판단이 갈릴 수 있다. 문구 예시를 한 줄 주면 좋다.
- 범위는 적절하다. P1/P4가 확정되기 전에 태스크 1 계산 함수를 시작해도 상수 한 곳 변경으로 대응 가능하다.
